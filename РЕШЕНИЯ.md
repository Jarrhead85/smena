# Журнал продуктовых и архитектурных решений

## Как менять решение

Не переписывать принятое решение молча. Добавить новую запись с датой, причиной, альтернативами, последствиями и списком документов/тестов для обновления. Решения со статусом «Принято» являются обязательными для агентов.

## ADR-001 — Личный локальный MVP

**Статус:** принято.

Одна медсестра, одно Android-устройство, одна активная смена. Без аккаунтов, backend, синхронизации, совместной работы и МИС.

## ADR-002 — .NET MAUI и Android

**Статус:** принято.

C#, .NET 10 LTS, `net10.0-android`, XAML, MVVM. Минимум Android 8.0/API 26 как рабочая рамка; проверить фактический парк до пилота. Preview-версии запрещены.

## ADR-003 — GigaChat как источник черновика

**Статус:** принято.

Прямой REST API, Authorization Key в настройках, фото через file storage и attachments. Модель возвращает JSON 1.0. Обязательное ручное подтверждение всего импорта. Отдельный OCR не включён до исследования качества.

## ADR-004 — Офлайн-планировщик

**Статус:** принято.

После сохранения смена, редактирование, статусы, история и уведомления работают локально. Только GigaChat требует сети. Никакого периодического фонового трафика.

## ADR-005 — Два напоминания

**Статус:** принято.

Предварительное за 10 минут по умолчанию и основное в назначенное время. Интервал 0–60 минут. Неточный fallback молча запрещён. Отказ разрешения виден постоянно.

## ADR-006 — Статусы без автопропуска

**Статус:** принято.

Pending, Done, Skipped. Overdue вычисляется. Пропуск не выставляется автоматически; причина пропуска и полный аудит не входят в MVP.

## ADR-007 — Данные и хранение

**Статус:** принято.

БД шифруется, секреты в SecureStorage, access token в памяти. Фото удаляются после импорта по умолчанию. История — 30 дней по умолчанию с настройками 7/30/90/бессрочно. Cloud backup чувствительных данных отключён.

## ADR-008 — UI

**Статус:** принято.

Нативный спокойный Android UI, три нижних раздела, хронологическая лента, крупное время, системный шрифт, светлая/тёмная тема, доступность AA. Без ИИ-чата, градиентов, эмодзи и декоративных шаблонов.

## ADR-009 — Граница эксплуатации

**Статус:** принято.

Прототип использует только синтетические/обезличенные данные. Реальный пилот требует организационного согласования обработки данных, устройств, установки, поддержки и эксплуатационных инструкций.

## ADR-010 — Реализация локального шифрования

**Статус:** принято 10.11.2026 для технического MVP.

EF Core использует `Microsoft.EntityFrameworkCore.Sqlite.Core` и только `SQLitePCLRaw.bundle_e_sqlcipher` 2.1.11, без одновременного native bundle обычного SQLite. DbContext владеет соединением, создаваемым из connection string. Retained photos шифруются AES-256 со случайным IV; ключ находится в SecureStorage. Миграция и шифрование файла проверены integration-тестами на хосте; Android Keystore/SQLCipher device gate остаётся открытым.

## ADR-011 — Явное завершение проверки импорта

**Статус:** принято 10.11.2026 для технического MVP.

Страница получает отдельное состояние `Excluded`, не смешиваемое с отменой всей сессии. Исключение доступно только после предупреждения и удаляет черновики этой страницы. Confirm запрещён для незавершённых и ошибочных страниц. Пустой итог требует отдельного параметра подтверждения, который выставляется только после явного согласия пользователя. Новое значение enum добавлено в конец, поэтому схема БД и существующие числовые значения не меняются; миграция не требуется.

## ADR-012 — Поток изображения на каждую попытку

**Статус:** принято 10.11.2026 для технического MVP.

`RecognitionRequest` передаёт фабрику открытия изображения. Это исключает повторное использование Stream, уже освобождённого `StreamContent`, при 401, сетевом retry и 5xx. Сервис распознавания владеет и освобождает поток каждой попытки; отмена задержки retry запрещает следующую попытку.

## ADR-013 — Состояния и диагностика Android-напоминаний

**Статус:** принято 10.11.2026 для технического MVP.

Каждая синхронизация сначала отменяет оба старых PendingIntent с различимыми Intent.Data. Редактирование также удаляет показанные уведомления назначения, потому что их содержимое могло устареть; обычный resync не удаляет уже показанные. `Dispatching` атомарно захватывает обработку, `Posted` фиксирует только успешный вызов Notify, а не прочтение. Старые `Delivered` остаются читаемыми как legacy. Новые enum добавлены в конец, схема БД не изменилась, поэтому EF-миграция не нужна.

Доступность включает глобальное разрешение уведомлений, канал `shift_assignments` с Importance выше None и exact alarm permission. Для каждой причины есть отдельный текст и системный переход. Проверочное уведомление содержит только общий текст.

## ADR-014 — Ограниченное восстановление прерванной доставки

**Статус:** принято 11.11.2026 для технического MVP; дополняет ADR-013.

`Dispatching` нельзя безусловно возвращать в `Scheduled`: прошедшее событие иначе не попадает в синхронизацию будущих. При инициализации прерванная доставка активного Confirmed + Pending назначения переводится в `Planned`, если время ещё в будущем; в `RecoveryPending`, если прошло не более 15 минут; в `Failed` с `SchedulingFailed`, если окно истекло. Для неактивной смены и неподтверждённого/обработанного назначения запись отменяется. `RecoveryPending` немедленно планируется повторно; стабильный notification ID предотвращает независимые дубли при неопределённом исходе после Notify.

Обычный resync больше не сбрасывает историю `Posted`, legacy `Delivered`, `Cancelled` или активную `Dispatching` и выбирает только актуальные будущие и восстановимые события. Альтернатива — массовая повторная доставка всех прошедших событий — отклонена. Схема БД не меняется: `RecoveryPending` добавлен в конец enum.

Обновлены FR-NOTIFY-009, модель состояний и сценарии Receiver/recovery. Host-тесты инициализации проверяют конечные состояния; фактические process-death/reboot сценарии остаются отдельным device gate.

## Открытые технические вопросы, закрываемые spikes

- Конкретная доступная vision-модель GigaChat и измеренное качество.
- Контрольные устройства, Android-проверка SQLCipher/retained photos и фактическое поведение exact alarms/Doze.
- Необходимость настройки цепочки сертификатов на целевых устройствах.
- Инструмент UI automation для MAUI device tests.

Эти вопросы не разрешаются выдуманными фактами в коде или документации.
