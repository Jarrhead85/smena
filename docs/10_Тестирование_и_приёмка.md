# Стратегия тестирования и критерии приёмки

## 1. Уровни проверки

1. **Unit:** доменные правила, время, статусы, валидация, маппинг.
2. **Integration:** EF Core/SQLCipher, транзакции, миграции, GigaChat handlers с фиктивными ответами.
3. **Contract:** JSON Schema, OAuth и file lifecycle на безопасных тестовых данных.
4. **UI:** навигация, формы, состояния, доступность.
5. **Device:** реальные уведомления, reboot, permissions, camera, storage, Doze.
6. **Recognition evaluation:** отдельный набор обезличенных листов с заранее размеченными полями.
7. **Security:** log/backup/storage/TLS/notification проверки.

Сборка без ошибок не является приёмкой. Невозможность запустить device test фиксируется как незакрытый gate, а не как успех.

## 2. Тестовые данные

Все примеры синтетические. Набор распознавания включает:

- печатные строки и таблицы;
- рукописные записи с разным почерком;
- разные шаблоны больниц;
- переносы, сокращения, пустые ячейки;
- одинаковые ФИО и повторные процедуры;
- время до/после полуночи;
- повреждённые, тёмные, наклонные и обрезанные фото;
- нечитаемые поля, для которых правильный ответ — `null`.

Для каждого листа заранее размечаются назначения, критические поля, неразобранные строки и допустимые варианты сокращений. Разметка не создаётся самой моделью непосредственно перед оценкой.

## 4. Напоминания: device-приёмка

При выданных разрешениях и нормальном состоянии устройства:

- Advance и Due доставляются на контрольных устройствах;
- открытие ведёт к правильному назначению;
- Done из уведомления идемпотентно;
- перезагрузка восстанавливает только будущие события;
- при denied permission виден постоянный warning;
- после выдачи доступа alarms пересоздаются;
- после принудительной остановки поведение задокументировано, приложение не обещает невозможное;
- в Doze фактическая задержка измеряется и записывается.

Контрольный прогон: не менее 20 запланированных событий на каждом обязательном устройстве, включая reboot и Doze. Цель — 20/20 корректных доставок в заявленных условиях. Любая задержка >60 секунд расследуется и блокирует заявление о надёжности до разрешения.

## 5. GigaChat contract-тесты

- получение/кэширование токена; обновление до истечения;
- параллельные запросы не вызывают шторм OAuth;
- 401 → одно обновление токена, не бесконечный цикл;
- upload с `purpose=general`;
- корректный attachments ID;
- delete при success/failure/cancel;
- 429 и Retry-After;
- timeout и cancellation;
- невалидный JSON, code fence, пустой content, неизвестная schema version;
- критические `null`, неверное `25:99`, слишком длинные строки;
- ни один handler не выводит Authorization или тело в лог.

Реальный contract test использует только тестовое изображение без медицинских данных и отдельный тестовый ключ, не встроенный в репозиторий.

## 6. Оценка распознавания

Отчёт по каждой модели содержит:

- exact match для пациента, времени и процедуры;
- точность дополнительных полей;
- процент валидных JSON до/после одного retry;
- процент пропущенных и выдуманных назначений;
- долю случаев, где нечитаемое корректно помечено;
- среднее и 95-й процентиль времени обработки;
- стоимость/токены, если доступны.

Ориентиры для технического MVP на согласованном наборе: валидный JSON ≥99% после retry; выдуманные назначения — 0 в контрольном наборе; критические поля печатных листов ≥95% exact match. Эти ориентиры не заменяют обязательную проверку пользователем. Для реального пилота пороги и размер набора согласуются отдельно; недостаточное качество требует OCR/другой модели/ограничения шаблонов, а не снижения безопасности.

## 7. UX и accessibility

На каждом ключевом экране проверить:

- ширины 360 и 412 dp;
- светлую/тёмную тему;
- системный шрифт 100%, 150%, 200%;
- длинные строки и пустые дополнительные поля;
- TalkBack и порядок фокуса;
- контраст токенов и disabled/error/focus состояний;
- touch targets ≥48 dp;
- отсутствие горизонтального overflow;
- клавиатуру и сохранение формы;
- все видимые кнопки и назад;
- reduced motion.

Сценарный тест: новый пользователь создаёт смену, добавляет назначение вручную, выполняет его и находит в истории без посторонней подсказки. Ошибки и время выполнения записываются без медицинских данных.

## 8. Security acceptance

Все 10 проверок из `09_Безопасность_и_данные.md` обязательны. Дополнительно:

- dependency scan без непринятых критических/высоких уязвимостей;
- секреты отсутствуют в git history и APK/AAB;
- Release не содержит verbose HTTP logs;
- backup/restore не переносит ключи и медицинскую БД небезопасно;
- неправильный TLS-сертификат отклоняется.

## 9. Матрица устройств

Минимум перед пилотом:

- эмулятор с минимальным API 26;
- эмулятор/устройство с текущим target API;
- один реальный телефон Google/Android One или аналог;
- один Samsung;
- один устройство Xiaomi/Redmi/POCO или другого производителя с агрессивным энергосбережением, если присутствует в целевой группе.

Для каждого фиксировать модель, Android/API, версию приложения, разрешения, battery mode и результат. Если фактический парк иной, матрица обновляется до реального использования.

## 10. Release gates

### Технический MVP

- Все AT-001…AT-018 пройдены.
- Unit/integration/contract тесты и Android Release build успешны.
- Нет blocker/critical UI и security дефектов.
- Работает офлайн-план и восстановление после reboot.
- Нет известной потери подтверждённых данных.

### Экспериментальное распознавание

- Качество выбранной модели задокументировано.
- Обязательный Review и блокировка пустых полей проверены.
- Remote file lifecycle проверен.
- Реальные пациенты в тестах не использовались.

### Реальный пилот

Дополнительно требуются организационное согласование, утверждённые требования обработки данных, контрольный парк устройств, инструкция пользователя, защищённая установка и поддержка. Без них продукт остаётся прототипом.

## 11. Отчёт о проверке

Каждый агент завершает задачу записью:

```text
Изменено: [файлы/функции]
Проверено: [команды и фактические сценарии]
Не проверено: [с причиной]
Дефекты/риски: [ID и серьёзность]
Документация: [что обновлено]
```

Нельзя писать «всё протестировано» без перечисления фактических проверок.
