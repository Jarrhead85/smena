# Архитектура и техническая реализация

## 1. Технологические решения

- C#, **.NET 10 LTS**, `net10.0-android`.
- .NET MAUI с XAML; только Android в MVP.
- MVVM через `CommunityToolkit.Mvvm`.
- Встроенный DI `Microsoft.Extensions.DependencyInjection`.
- SQLite через EF Core 10 / `Microsoft.Data.Sqlite`; шифрование БД через поддерживаемый SQLCipher native bundle.
- `HttpClient` + `System.Text.Json` для GigaChat REST API; официального C# SDK не предполагается.
- `SecureStorage` для Authorization Key и ключа БД; access token только в памяти.
- Нативные `AlarmManager`, `NotificationManager`, `BroadcastReceiver` в `Platforms/Android`.
- `MediaPicker` для камеры/галереи; подготовка изображения через платформенный Android-код.
- xUnit для Core/Infrastructure; UI/device-тесты выбираются после исследования окружения.

Не использовать .NET 11 Preview, экспериментальный CoreCLR на Android, BlazorWebView или web-UI вместо нативного интерфейса. Минимальная цель MVP — Android 8.0 / API 26; фактический парк устройств проверяется до пилота. Target SDK — последняя стабильная версия, поддерживаемая зафиксированным .NET workload.

## 2. Архитектурный стиль

Небольшой модульный монолит с разделением на Core, Infrastructure и MAUI App. Clean Architecture применяется прагматично: без кучи интерфейсов ради интерфейсов, но внешние зависимости всегда отделены от доменных правил.

## 3. Поток зависимостей

`App → Core ← Infrastructure`. App определяет ViewModels и вызывает прикладные сервисы `IShiftService` и `IImportService`. Infrastructure реализует их поверх короткоживущих DbContext; отдельный слой универсальных repositories/use cases не введён. Core ничего не знает о MAUI, Android, `HttpClient`, EF Core или GigaChat DTO.

Платформенные реализации регистрируются в `MauiProgram`. Android API не размещаются в ViewModel.

## 4. Основные порты

```csharp
public interface IClock { DateTimeOffset UtcNow { get; } }
public interface IShiftService { /* смены, назначения, история, статусы */ }
public interface IImportService { /* сессии, страницы, черновики, Confirm/Cancel */ }
public interface IRecognitionService
{
    Task<RecognitionResult> RecognizeAsync(
        RecognitionRequest request, CancellationToken cancellationToken);
}
public interface IReminderScheduler
{
    Task<OperationResult> SynchronizeAssignmentAsync(
        Guid assignmentId, CancellationToken cancellationToken);
    Task<OperationResult> SynchronizeAllFutureAsync(CancellationToken cancellationToken);
    Task CancelForAssignmentAsync(Guid assignmentId, CancellationToken cancellationToken);
}
public interface ISecretStore { /* ключи, без логирования значений */ }
public interface IImagePicker { /* camera/gallery */ }
public interface IImageProcessor { /* поворот сохранённой страницы */ }
```

Полные сигнатуры находятся в `src/NurseShift.Core/Interfaces/Services.cs`. В операциях сохраняются cancellation, идентификаторы, optimistic concurrency и безопасный `OperationResult`.

## 5. Ключевые последовательности

### Подтверждение импорта

1. Use case получает `ImportSessionId` и текущий `RowVersion`.
2. Проверяет активную смену, критические поля, границы времени и обработку неразобранных строк.
3. В транзакции создаёт/связывает пациентов, подтверждает назначения, создаёт записи Reminder, закрывает ImportSession.
4. Фиксирует транзакцию.
5. Вызывает синхронизацию системных уведомлений.
6. При ошибке планирования сохраняет безопасный код ошибки и показывает постоянное предупреждение; не откатывает сохранённый план.
7. Запускает очистку локальных фото и удалённых файлов.

### Изменение назначения

1. Проверить состояние и версию.
2. Вычислить новые DueAtUtc и Reminder в памяти.
3. Сохранить назначение и reminder records атомарно.
4. Отменить прежние Android alarms по сохранённым request codes.
5. Создать новые alarms. Ошибка отражается в reminder state и UI.
6. Не полагаться на то, что запись в БД автоматически означает системную регистрацию.

### Выполнение из уведомления

1. Receiver получает только assignment ID и action, без медицинских полей в Intent extras.
2. Загружает назначение из БД.
3. Проверяет, что оно всё ещё Pending.
4. Обновляет статус и отменяет второе будущее напоминание.
5. Повторная доставка action идемпотентна.

## 6. GigaChat-клиент

Реализация разделена на:

- `GigaChatAuthClient` — OAuth, кэш токена с запасом истечения, учёт ключа/scope и потокобезопасное обновление.
- `GigaChatRecognitionService` — последовательный files upload → chat completion → delete, DTO и маппинг в черновики.
- `RecognitionResponseParser` — извлечение JSON и schema/domain validation.

Отдельные FileClient/ChatClient/Mapper не выделены: весь file/chat lifecycle согласованно находится в recognition service.

Никакой компонент не логирует тело запроса/ответа. Таймауты и ограниченные retry только для сетевых/5xx ошибок; 4xx валидации и авторизации не повторять автоматически. Подробности — в документе GigaChat.

## 7. Персистентность

EF Core используется с явными миграциями. DbContext не хранится как единый долгоживущий singleton. Операции используют короткие scope. Включить foreign keys. Индексы и уникальные ограничения приведены в модели данных.

Ключ шифрования БД создаётся случайно при первом запуске и хранится через защищённое хранилище. Потеря ключа делает БД нечитаемой; приложение должно безопасно сообщить о невозможности восстановления, не удаляя данные молча.

## 8. Локальные файлы

Фото находятся в app-private storage, не в публичной галерее. Временные файлы имеют случайные имена без ФИО. Пути не передаются внешним приложениям. При включённом сохранении `PhotoRetentionStore` шифрует содержимое через AES со случайным IV; 256-битный ключ хранится в `SecureStorage`. Открытый JPEG после финализации удаляется. Это подтверждено кодом, но device-проверка защищённого хранилища ещё не выполнена.

Фото в кэше до завершения импорта не считаются долговременным хранением. Cleanup запускается после подтверждения, отмены и при старте для orphaned temp files.

## 9. Обработка ошибок

Безопасные категории:

```text
NetworkUnavailable, Timeout, TlsValidationFailed, Unauthorized,
PermissionDenied, RateLimited, ServiceUnavailable, ResponseInvalid,
ImageTooLarge, ImageUnreadable, StorageUnavailable, SchedulingDenied,
SchedulingFailed, Unknown
```

Исключения не сериализуются в UI. Для разработки допускается diagnostic ID и техническая категория без данных. Не использовать `Exception.Message` как готовый пользовательский текст.

## 10. Ресурсы и производительность

- Холодный запуск до интерактивной ленты: цель ≤2 секунд на контрольном среднем устройстве.
- Прокрутка 200 назначений без заметных зависаний; использовать CollectionView virtualization.
- Не держать полноразмерные bitmap всех страниц одновременно.
- Максимум одна активная операция распознавания; страницы последовательно в MVP.
- Нет периодического сетевого фонового трафика.
- Список времени обновляется только на видимом экране; напоминания не зависят от таймера UI.

## 11. Сборка и конфигурация

`Directory.Build.props` включает nullable, последний стабильный языковой режим SDK и warnings as errors для CI после первичной стабилизации. `global.json` фиксирует .NET SDK. NuGet-версии фиксируются; не использовать плавающие `*`.

Не создавать секретные `appsettings`. Несекретные значения по умолчанию: API base URL, OAuth URL, timeout, размеры изображения. Release и Debug отличаются только логированием и оптимизацией, не правилами безопасности.

## 12. Что нельзя делать без ADR

- Добавлять backend, аккаунты или синхронизацию.
- Менять GigaChat на другой сервис.
- Добавлять аналитику/crash SDK.
- Ослаблять TLS, шифрование или обязательное подтверждение.
- Переносить напоминания в неточные без явного поведения и предупреждения.
- Менять публичный JSON-контракт без версии и миграции.
