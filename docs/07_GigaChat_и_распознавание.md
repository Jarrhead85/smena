# Интеграция GigaChat и распознавание назначений

Сведения об API проверены по официальной документации 10 ноября 2026. Ссылки — в `14_Внешние_источники.md`.

## 1. Подход

MVP использует мультимодальный GigaChat напрямую с Android-устройства. Изображение загружается в хранилище GigaChat, затем его ID передаётся в `attachments` запроса chat completion. Модель возвращает строго проверяемый JSON-черновик.

Отдельный OCR в MVP не добавляется. Если исследование качества покажет недостаточную точность, ADR может ввести отдельный OCR для текста и оставить GigaChat для структурирования. Нельзя незаметно добавить второго внешнего обработчика медицинских данных.

## 2. Конфигурация

```text
ApiBaseUrl  = https://api.giga.chat/v1
OAuthUrl    = https://ngw.devices.sberbank.ru:9443/api/v2/oauth
Scope       = GIGACHAT_API_PERS | GIGACHAT_API_B2B | GIGACHAT_API_CORP
Model       = выбирается пользователем; без жёстко зашитого production ID
Timeout     = 60 секунд на запрос по умолчанию
```

Настройки содержат Authorization Key, scope и model. Не хранить Client Secret отдельно, если пользователь вводит готовый Authorization Key. Не сохранять access token постоянно.

## 3. OAuth

1. Получить ключ из `ISecretStore` только на время сетевой операции.
2. Сформировать `POST /api/v2/oauth` с:
   - `Authorization: Basic <Authorization Key>`;
   - `RqUID: <новый GUID/UUID4>`;
   - `Content-Type: application/x-www-form-urlencoded`;
   - телом `scope=<scope>`.
3. Получить `access_token` и `expires_at`.
4. Кэшировать токен только в памяти, с защитой от параллельного обновления.
5. Обновлять заранее с запасом не менее 60 секунд. Официальный срок токена — 30 минут.
6. При 401 на API один раз обновить токен и повторить запрос, если операция идемпотентна или использует известный remote ID. Повторная загрузка должна удалять предыдущий remote file, если он был создан.

Не логировать Authorization header, RqUID вместе с данными, access token, ответ OAuth или stack trace с HttpRequestMessage.

## 4. Загрузка и удаление файла

Для каждой страницы:

1. Подготовить JPEG с корректной ориентацией.
2. Проверить читаемость по техническим признакам и размер. Официальный максимум изображения — 15 МБ; целевой предел приложения — 10 МБ.
3. Выполнить `POST /files` с `purpose="general"` и MIME `image/jpeg`.
4. Сохранить `RemoteFileId` в защищённой БД до подтверждения удаления.
5. Передать ID в chat request.
6. После получения финального ответа или отмены вызвать `POST /files/{file_id}/delete` в `finally`-подобной ветке очистки.
7. При ошибке удаления установить `RemoteDeletePending=true`. Повторить при следующей явной сетевой операции.

Удаление через API является обязательным действием приложения, но не заменяет проверку политики хранения провайдера. UI не должен утверждать, что данные гарантированно стёрты из всех систем провайдера.

## 5. Chat-запрос

- Использовать `POST /chat/completions` на текущем API base URL.
- Одно изображение на одно сообщение; страницы обрабатываются последовательно.
- `stream=false`, низкая температура (`0.0–0.1`).
- В user message передать один `attachments: [remoteFileId]`.
- В system prompt передать схему и правила; в user prompt — только технический контекст смены (дата/границы/пояс), без лишней истории.
- Не использовать `response_format`, пока его поддержка выбранной моделью не подтверждена. Корректность обеспечивается промптом, JSON Schema и доменной валидацией.

Официально одно сообщение поддерживает одно изображение, а запрос может содержать несколько; MVP всё равно использует один файл на операцию для надёжного сопоставления и повтора.

Пример структуры без реальных данных находится в `../contracts/recognition-request.example.json`.

## 6. Системный промпт

Актуальный шаблон хранится в `../contracts/recognition-system-prompt.txt`. Основные правила:

- только извлечение, без медицинских знаний;
- не дополнять непрочитанное;
- `null` для неизвестного;
- время `HH:mm` в 24-часовом формате или `null`;
- сохранять исходные названия и дозировки;
- не объединять строки и пациентов;
- вернуть неразобранные строки;
- вернуть JSON без Markdown и комментариев;
- каждое назначение снабдить дословным `source_excerpt`, если возможно;
- `needs_review=true` при любой неоднозначности.

Промпт не является механизмом безопасности. Даже идеальный ответ остаётся черновиком.

## 7. JSON-контракт

Корень:

```json
{
  "schema_version": "1.0",
  "assignments": [],
  "unparsed_lines": []
}
```

Назначение:

```json
{
  "patient_name": "Иванов Иван Иванович",
  "room": "12",
  "bed": "3",
  "time": "06:00",
  "procedure": "Общий анализ крови",
  "dosage": null,
  "comment": null,
  "source_excerpt": "Иванов, 6:00, общий анализ крови",
  "needs_review": false,
  "review_reason": null
}
```

`patient_name`, `time`, `procedure` в схеме допускают `null`, потому что нечитаемость должна быть представлена без выдумывания. Доменный Confirm затем запрещает пустые критические поля.

Машинная схема: `../contracts/recognition-response.schema.json`. Версия `schema_version` обязательна. Несовместимая версия отклоняется, а не угадывается.

## 8. Разбор ответа

1. Проверить HTTP status и наличие ожидаемого message content.
2. Убрать только один внешний Markdown fence, если он присутствует. Не извлекать произвольный JSON из длинного текста regex.
3. Ограничить размер ответа и глубину/количество элементов на уровне клиента.
4. Десериализовать `System.Text.Json` в DTO; запретить trailing commas и комментарии.
5. Проверить JSON Schema и `schema_version`.
6. Нормализовать whitespace, но не менять смысл/регистр медицинских строк.
7. Проверить длины, формат времени, максимум 500 записей на страницу и допустимые enum/bool.
8. Преобразовать время в контексте смены; ошибочное/вне смены — `needs_review` с безопасной причиной.
9. Сохранить черновик и привязку к SourceImage.
10. Не создавать Reminder и не менять ExecutionStatus.

При невалидном JSON допускается один автоматический повтор запроса с той же страницей. После повторной ошибки страница переходит в Failed, остальные страницы сохраняются.

## 9. Проверка качества

До выбора модели провести spike на обезличенном наборе:

- печатные таблицы разных форм;
- рукописные строки разным почерком;
- наклон, тени, блики, низкая контрастность;
- многостраничность;
- ночная смена;
- пустые клетки, переносы строк, сокращения;
- повторы и одинаковые ФИО;
- намеренно нечитаемые поля.

Метрики: точность каждого критического поля, процент выдуманных записей, доля валидных JSON, время страницы, стоимость/токены, доля ошибочно пропущенных строк. Числовая уверенность модели не используется как доказательство.

Модель утверждается для MVP только после документированного результата. Список моделей получать через `GET /models`; доступность vision у выбранной модели проверять реальным тестовым изображением без медицинских данных.

## 10. Ошибки и retry

| Ситуация | Поведение |
|---|---|
| Нет сети/timeout | Сохранить страницу, предложить повтор; экспоненциальный retry не более 2 раз |
| 401 | Обновить токен один раз; затем предложить проверить ключ/scope |
| 403 | Не повторять; проверить доступ и X-Client-ID, если он используется |
| 413/слишком большой файл | Не отправлять повторно; переснять или подготовить заново |
| 422 | Не повторять автоматически; сохранить понятную ошибку обработки |
| 429 | Один повтор с учётом Retry-After, затем показать лимит |
| 5xx | Не более 2 retry с jitter; не терять остальные страницы |
| TLS | Не отключать проверку; показать инструкцию по доверенным сертификатам |
| Невалидный JSON | Один повтор, затем Failed |
| Отмена | Не начинать следующую страницу, удалить текущий remote file по возможности |

Все retry учитывают CancellationToken. Пользователь видит прогресс и может перейти к ручному вводу.

## 11. Безопасность

- Сетевой трафик только HTTPS; проверка цепочки сертификатов всегда включена.
- Certificate pinning не добавлять без плана обновления и ADR.
- Не использовать `DangerousTrustManager`, accept-all handler или отключение hostname verification.
- Не записывать ответ модели в diagnostic log.
- Тестовые HttpClient handlers автоматически удаляют/маскируют Authorization и тело.
- Не отправлять существующий план или другие страницы вместе с текущим запросом без необходимости.
- Реальные фото не использовать для разработки и screenshot tests.
