# Напоминания и офлайн-надёжность

## 1. Цель

Подтверждённые назначения должны напоминать о себе без сети, после сворачивания приложения и перезагрузки телефона. При этом приложение обязано честно показывать ограничения Android и не выдавать запись в БД за гарантированно зарегистрированный системный alarm.

## 2. Архитектура

Использовать нативный Android-код:

- `AlarmManager` для времени срабатывания;
- `NotificationManagerCompat` и каналы для отображения;
- `BroadcastReceiver` для alarm, boot, time/timezone и permission changes;
- локальная БД как источник назначений и сохранённых request codes;
- `IReminderScheduler` как единая точка синхронизации.

WorkManager не используется как замена точному времени процедуры. Он может выполнять отложенную очистку, но не основные напоминания.

## 3. Разрешения и манифест

Проверить и реализовать по целевым API:

- `POST_NOTIFICATIONS` для Android 13+;
- `SCHEDULE_EXACT_ALARM` для пользовательского специального доступа к точным будильникам;
- `RECEIVE_BOOT_COMPLETED` для восстановления после перезагрузки;
- receivers должны иметь корректные exported/permission настройки и не принимать неявные небезопасные Intent от других приложений.

`USE_EXACT_ALARM` не выбирать автоматически: он предназначен для ограниченных сценариев и имеет ограничения распространения. Выбор должен быть согласован с фактической классификацией приложения. По умолчанию проект использует `SCHEDULE_EXACT_ALARM` и явную обработку отказа.

Перед каждым exact scheduling проверять `canScheduleExactAlarms()`, когда применимо. Перед запросом доступа объяснить пользователю результат. Отказ не блокирует план и ручной ввод.

## 4. Планирование

Для подтверждённого Pending назначения вычислить:

```text
advanceAt = dueAt - shiftOrAssignmentLeadMinutes
dueAt     = назначенное время
```

MVP использует глобальный интервал, зафиксированный при создании назначения. При смене настройки существующие записи не меняются без явного действия.

Правила:

- `lead=0` — только Due;
- Advance в прошлом, Due в будущем — только Due;
- оба в прошлом — ни одного;
- Done/Skipped/Completed — отмена обоих;
- после Confirm — синхронизация всех новых назначений;
- при повторной синхронизации сначала отменить старые PendingIntent по сохранённым request codes, затем создать актуальные.

Использовать exact API, допускающий работу в idle при наличии разрешения. Не применять `setAlarmClock` без необходимости и ADR.

## 5. Идентичность Intent и PendingIntent

Каждый Reminder имеет стабильный уникальный `AndroidRequestCode`. Intent должен однозначно отличаться по action/data и содержать только технические ID:

```text
action: ru.smena.app.action.REMINDER
extra:  reminder_id (GUID string)
```

Не передавать ФИО, процедуру, палату или комментарий в Intent extras: Receiver загружает актуальные данные из БД. PendingIntent создаётся с Immutable и подходящим UpdateCurrent/CancelCurrent поведением. Не генерировать request code заново при каждом запуске.

## 6. Получение alarm

Receiver:

1. Получает reminder ID.
2. Загружает Reminder, Assignment и Shift.
3. Проверяет, что Reminder Scheduled, Assignment Confirmed + Pending, Shift Active.
4. Проверяет, что событие не устарело и не отменено.
5. Получает актуальные данные из БД и показывает уведомление.
6. Отмечает Delivered; повторная доставка не создаёт бесконечные дубли.

Если приложение обновило запись между отправкой Intent и доставкой, stale event молча игнорируется с безопасным diagnostic code, без медицинского содержимого.

## 7. Уведомления

Создать канал высокой важности для назначений. Название и описание канала понятны пользователю. Не менять ID канала после выпуска без миграции. Звук/вибрация управляются системными настройками канала; приложение даёт ссылку на них.

Содержимое:

- предварительное: время до процедуры и название;
- основное: назначенное время и название;
- расширенный текст: пациент, палата/койка;
- при private lock-screen режиме публичная версия не содержит медицинских данных.

Действия: открыть назначение; «Выполнено» для основного уведомления. Action Intent содержит только assignment ID и защищён от повторной обработки. Full-screen intent не используется.

## 8. Перезагрузка и системные события

После `BOOT_COMPLETED` выполнить минимальную инициализацию БД и `SynchronizeAllFutureAsync`:

- пересоздать будущие alarms для Active Shift + Confirmed + Pending;
- не показывать массово просроченные события;
- отметить ошибки и показать предупреждение при следующем открытии;
- не обращаться к GigaChat.

Также обработать:

- `TIME_CHANGED` — пересчитать/проверить alarms без изменения DueLocal;
- `TIMEZONE_CHANGED` — сохранить локальное расписание пояса смены, пересчитать UTC при необходимости и показать предупреждение;
- `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` — проверить доступ и выполнить resync;
- `PACKAGE_REPLACED` — resync после обновления;
- возврат приложения на передний план — проверить разрешения и состояние scheduler.

## 9. Отказ разрешений

Если разрешения нет:

- план сохраняется;
- Reminder получает Failed с `SchedulingDenied`;
- на главном экране отображается постоянный banner;
- настройки содержат кнопку в системные параметры;
- после выдачи разрешения выполняется resync.

Нельзя показывать «Напоминания включены». Нельзя молча переходить на неточные alarms. Неточный режим не входит в MVP; если он появится, потребуется отдельный явный выбор пользователя и ADR.

## 10. Энергосбережение

Приложение объясняет, что агрессивные настройки производителя могут влиять на доставку. Не запрашивать игнорирование оптимизации батареи по умолчанию. Если device-тесты показывают систематическую проблему, добавить инструкцию для конкретного производителя и оценить разрешение отдельно.

Никакое приложение не должно обещать абсолютную доставку при выключенном телефоне, отключённых уведомлениях или принудительной остановке. Эти условия входят в эксплуатационную инструкцию.

## 11. Офлайн-функции

Без сети обязаны работать:

- создание/завершение смены;
- ручной ввод, редактирование, удаление;
- просмотр ленты и истории;
- смена статусов;
- локальные напоминания;
- очистка истории;
- изменение несетевых настроек.

Без сети не работают: проверка подключения, получение моделей, upload/chat/delete GigaChat. Удаление локальных фото и плана не зависит от remote delete.

## 12. Обязательные тесты

- оба напоминания; lead=0; due через 1 минуту; все времена в прошлом;
- изменение due после scheduling; Done между Advance и Due;
- удаление назначения и завершение смены;
- перезагрузка до Advance и между Advance/Due;
- отказ/отзыв notification и exact alarm permission;
- переход времени и часового пояса;
- принудительная остановка и повторный запуск;
- Doze и контрольные устройства производителей;
- холодный запуск по notification и action «Выполнено»;
- двойная доставка Receiver без дублирования статуса/уведомления;
- отсутствие медицинских данных в Intent, публичной версии уведомления и логах.

Результаты фиксируются по модели устройства, Android API, настройкам батареи и фактическому времени доставки. Unit-тесты не заменяют эти сценарии.
