# Риски, исследования и критерии решений

## 1. Качество рукописного распознавания

**Риск:** модель пропускает строки или уверенно выдумывает значения.

**Исследование:** размеченный набор реальных по структуре, но обезличенных листов; сравнение доступных vision-моделей.

**Критерий решения:** точность критических полей, 0 выдуманных назначений в контрольном наборе, стабильный JSON, разумная задержка. При недостаточном результате: ограничить шаблоны, улучшить захват, добавить OCR или оставить только ручной ввод. Обязательная проверка не удаляется.

## 2. Точные напоминания на Android

**Риск:** отказ в разрешении, Doze, ограничения производителя, потеря alarms после reboot.

**Исследование:** нативный AlarmManager spike на контрольных устройствах.

**Критерий решения:** 20/20 событий в заявленных условиях, корректный resync и видимая ошибка при denied. При невозможности — честно ограничить поддержку устройств, а не скрывать проблему.

## 3. TLS и сертификаты GigaChat

**Риск:** устройство не доверяет необходимой цепочке; разработчик пытается отключить проверку.

**Исследование:** OAuth/upload на минимальном и текущем Android API с чистым устройством.

**Критерий решения:** успешное соединение при документированной доверенной конфигурации. Отключение проверки не является допустимым решением.

## 4. SQLCipher и .NET MAUI

**Риск:** несовместимость native bundle, миграции или производительность.

**Исследование:** create/read/restart/migration/backup test.

**Критерий решения:** файл БД нечитаем без ключа, стабильный restart и миграция. Если выбранный пакет не поддерживается, выбрать поддерживаемую альтернативу через ADR, не оставлять открытую БД.

## 5. Хранение исходных фото

**Риск:** фото остаются в кэше, gallery, backup или recents.

**Исследование:** файловый аудит после каждого перехода ImportSession.

**Критерий решения:** default delete подтверждён, retained content зашифрован, orphaned cleanup работает, backup исключён.

## 6. Потеря черновика при process death

**Риск:** пользователь повторно сканирует лист или дважды подтверждает импорт.

**Исследование:** принудительное уничтожение процесса на Preparing, Uploading, Recognizing, Review, Confirm.

**Критерий решения:** безопасное восстановление; неизвестный результат запроса не приводит к Confirm; повторный Confirm идемпотентен.

## 7. Часовые пояса и переходы времени

**Риск:** процедура сдвигается после поездки/изменения настроек или становится неоднозначной.

**Исследование:** ночная смена, timezone change, manual time change, ambiguous/invalid local time.

**Критерий решения:** DueLocal смены сохраняется, UTC/resync объяснимы, неоднозначность требует ручного выбора.

## 8. Перегрузка интерфейса

**Риск:** попытка показать все поля и статусы делает ленту нечитаемой для старших пользователей.

**Исследование:** сценарные тесты с 200% font, длинными строками, TalkBack и одной рукой.

**Критерий решения:** критические действия остаются видимыми и озвученными, нет обрезания времени/кнопок. Сокращать вторичный контент, не уменьшать шрифт.

## 9. Прямое хранение Authorization Key на телефоне

**Риск:** компрометация устройства раскрывает ключ и квоту пользователя.

**Решение MVP:** SecureStorage, no logs/backups, удаление/замена ключа. Для организационной эксплуатации оценить управляемые устройства и backend token broker через отдельный ADR; не добавлять backend в MVP молча.

## 10. Реальные медицинские данные

**Риск:** разработка или пилот начинаются без согласования обработки данных.

**Критерий:** до разрешения используются только синтетические/обезличенные данные. Организационный пилот — отдельный release gate. Техническая готовность не означает разрешение на эксплуатацию.

## 11. Что должно быть записано после каждого spike

- дата, версии SDK/OS/модели;
- минимальный воспроизводимый сценарий;
- фактические результаты и ограничения;
- выбранное решение и отклонённые альтернативы;
- влияние на документы и тесты;
- ссылка на новую запись в `РЕШЕНИЯ.md`.
